# GAL Kubernetes Safe-Mode Management

This skill helps an admin create a restricted Kubernetes kubeconfig, mount it
into GAL safe mode, and manage limited namespace-scoped writes through an
explicit policy gate.

Security boundaries:

- GAL safe mode hides the user's real `~/.kube` and Kubernetes/cloud credential
  environment variables.
- Kubernetes RBAC is the authority for API permissions.
- This skill's script is a policy gate for generating safe RBAC and performing
  guarded write operations. It must not read, print, or copy kubeconfig tokens.
- Destructive operations are out of scope. Do not grant or execute `delete` or
  `deletecollection`.

> **CAUTION — Read before executing any command in this skill.**
>
> This skill generates real Kubernetes RBAC and ServiceAccount tokens that
> directly affect cluster security. A wrong configuration can grant excessive
> permissions or leak credentials. Follow these rules strictly:
>
> 1. **Always dry-run first.** Every write command supports `--dry-run`. Use it
>    to review the generated YAML or kubeconfig structure before applying.
> 2. **Never print or log tokens.** The script redacts tokens in `--dry-run`
>    output. Do not work around this — do not `cat` the kubeconfig, do not echo
>    `kubectl create token` output, do not paste token values into chat.
> 3. **Never mount the admin kubeconfig.** Only the restricted kubeconfig
>    generated by `gen-kubeconfig` may be mounted into safe mode. The admin
>    kubeconfig has cluster-admin privileges — mounting it defeats the entire
>    purpose of this skill.
> 4. **Verify after every change.** After applying RBAC or generating a
>    kubeconfig, run `kubectl auth can-i --list` from the runtime agent to
>    confirm the permissions match the policy. If you see `*` verbs or
>    `cluster-admin`, something is wrong — fix it before proceeding.
> 5. **Refuse protected namespaces.** If the user asks to add write permissions
>    for a protected namespace (kube-system, default, etc.), refuse. Do not
>    generate or apply any YAML.
> 6. **Keep management and runtime isolated.** The management agent generates
>    credentials; the runtime agent consumes them. Never run `gen-kubeconfig`
>    or `renew-token` from the runtime agent — it does not have the privileges,
>    and attempting it signals a configuration error.

## Installation guide (cross-agent: management / runtime isolation)

This skill is designed for **management/runtime isolation**: one agent with real
cluster admin privileges manages RBAC and generates the restricted kubeconfig; a
separate agent in safe mode runs guarded operations using only that restricted
kubeconfig. Never combine both roles in a single agent.

When a user asks to install/set up this skill, walk through the following:

### Step 0 — Explain the architecture and ask about agents

Tell the user:

> This skill uses a cross-agent design: a **management agent** (no safe mode,
> has real cluster credentials) creates RBAC and generates the restricted
> kubeconfig; a **runtime agent** (safe mode, restricted kubeconfig only) runs
> guarded kubectl operations. They must be two different agents.

Then ask which mode the user wants:

1. **Use existing agents** — the user names the management agent and the runtime
   agent.
2. **System-create mode** — GAL checks for `ops` and `ops-admin`; creates them
   if missing, then wires everything up.

### Step 1a — Use existing agents

Ask the user to specify:

- **Management agent**: the one that will run `readonly-rbac`, `namespace-write-rbac`,
  `gen-kubeconfig`. It must NOT have safe_mode enabled and must have real cluster
  access (host `~/.kube` visible).
- **Runtime agent**: the one that will run `guarded-apply`, `restart`, `backup`,
  `list-policy` inside safe mode.

Then:
- Add `gal-k8s-safe` to the `skills:` list of **both** agents.
- On the **runtime agent**, add the safe_mode mount (step 4 below).
- The **management agent** does NOT get safe_mode or the mount.

### Step 1b — System-create mode

Check whether agents `ops` and `ops-admin` already exist (`gal agent list` or
read `~/.gal/agents/*.yaml`):

- If `ops-admin` **does not exist**, create it:
  - No safe_mode.
  - Tools: `file_read`, `file_write`, `file_edit`, `bash`, `grep`,
    `interactive`, `symbols`.
  - Skills: `gal-k8s-safe`.
  - Models: inherit from default agent or prompt the user.
  - This is the **management agent**.

- If `ops` **does not exist**, create it:
  - `safe_mode.enabled: true` with the kubeconfig mount (step 4).
  - Tools: `file_read`, `file_list`, `grep`, `bash`, `symbols`, `interactive`.
  - Skills: `gal-k8s-safe`.
  - Models: inherit from default agent or prompt the user.
  - This is the **runtime agent**.

- If **both already exist**:
  - Add `gal-k8s-safe` to `ops-admin`'s `skills:` list (management commands).
  - Add `gal-k8s-safe` to `ops`'s `skills:` list (runtime commands).
  - Add the safe_mode mount to `ops` if not already present.
  - Do NOT modify any other settings of existing agents without asking.

### Step 2 — Confirm the plan with the user

Before touching anything, summarize:
- Management agent: which agent, what it will do (RBAC + gen-kubeconfig).
- Runtime agent: which agent, safe_mode mount path.
- Ask for explicit confirmation.

### Step 3 — Generate the restricted kubeconfig (management agent)

Run from the **management agent** session (or `/admin` if the management agent
is the admin itself). Follow steps 1–3 of "Generate a restricted kubeconfig"
below (readonly-rbac → optional namespace-write-rbac → gen-kubeconfig).

### Step 4 — Configure the runtime agent safe_mode mount

Edit the **runtime agent** YAML:

```yaml
safe_mode:
  enabled: true
  mounts:
    - source: ~/.safe-mount-dir/gal-k8s-safe/kubeconfig
      target: ~/.kube/config
      mode: ro
```

### Step 5 — Verify

From the **runtime agent** session:
1. `_status` shows Kubernetes credential dirs/env hidden, `~/.kube/config` mounted read-only.
2. `kubectl config current-context` shows the restricted context.
3. `kubectl auth can-i --list` shows only the granted verbs.

### Token renewal

The restricted kubeconfig token expires after the configured duration (default
72h). When it expires, switch to the **management agent** and run `renew-token`.
This reads the existing kubeconfig to preserve server/CA/context, requests a new
SA token, and rewrites the file in place with mode 0600 — no need to recreate
RBAC or re-run `gen-kubeconfig`.

## Permission model

Default access is cluster-wide read-only:

- `apiGroups: ["*"]`
- `resources: ["*"]`
- `verbs: ["get", "list", "watch"]`

This intentionally means all Kubernetes resources are readable, including custom
resources and secrets if the cluster allows RBAC wildcard reads. If the user does
not want secrets readable, do not use this default; create a narrower custom
read-only ClusterRole instead.

Writable access is opt-in per namespace. A namespace write grant allows only:

- verbs: `get`, `list`, `watch`, `create`, `update`, `patch`
- no `delete`, no `deletecollection`
- no escalation verbs such as `bind`, `escalate`, `impersonate`, or `approve`
- no writes to CRDs, RBAC, service accounts, secrets, namespaces, nodes, storage
  primitives, admission webhooks, or other low-level/platform resources

Allowed writable resource groups are limited to:

- core: `configmaps`, `services`
- apps: `deployments`, `statefulsets`, `daemonsets`, `replicasets`
- batch: `jobs`, `cronjobs`
- networking.k8s.io: `ingresses`

Use this for configuration changes, rollout/redeploy style operations, and safe
manifest apply. Do not use it for cluster administration.

## Protected namespaces

The policy script refuses write grants and write operations for protected
namespaces. Defaults:

- `kube-system`
- `kube-public`
- `kube-node-lease`
- `default`
- `cert-manager`
- `ingress-nginx`
- `istio-system`
- `linkerd`
- `monitoring`
- `logging`
- `argocd`
- `flux-system`

If the user asks to add write permission for a protected namespace, refuse. Do
not generate YAML and do not apply anything.

## Backups for write operations

Every write operation performed through the policy script creates a backup first
when an existing generated or target object is present. Missing objects are
reported as `Backup skipped (not found)` because there is no previous state to
save.

Default backup directory:

```text
~/.safe-mount-dir/gal-k8s-safe/backups
```

The admin may override it with `GAL_K8S_SAFE_BACKUP_DIR`, but it must not be
under `~/.gal`.

You do **not** need to add this directory to `safe_mode.extra_paths`. Backups are
written by this skill's script tool (`policy.py`), which runs outside the sandbox
with full host permissions and creates the directory itself. Safe mode's
read-only home restriction only applies to the `bash` and file tools, not to skill
script tools — so the backup path is writable regardless of safe-mode config.

Only add the backup directory to `safe_mode.extra_paths` with `rw` mode if you
specifically want the agent to read or write those backup files through the `bash`
or file tools (e.g. to inspect a saved YAML manually). This is normally
unnecessary — the script manages backups on its own.

Default retention is 15 days. The script prunes older `*.yaml` backups whenever
it performs a backup.

## Safe-mode kubeconfig mount

GAL safe mode hides the user's real Kubernetes/cloud credential locations and
credential environment variables, including `~/.kube` and `KUBECONFIG`.

Expose only a trusted, pre-restricted kubeconfig:

```yaml
safe_mode:
  enabled: true
  mounts:
    - source: ~/.safe-mount-dir/gal-k8s-safe/kubeconfig
      target: ~/.kube/config
      mode: ro
```

- `source` is the host-side restricted kubeconfig.
- `target` is the path inside the sandbox. Keep it as `~/.kube/config` unless the
  user has a specific CLI requirement.
- `mode` should be `ro` for kubeconfig credentials.
- If the source file is missing, GAL skips the mount; it does not read or create
  the kubeconfig for you.

## Script tool

After loading this skill, GAL registers:

```text
skill_gal-k8s-safe_policy
```

The script accepts command-line arguments through the tool's `args` field. It is
safe to use for policy validation and YAML generation. Applying RBAC or workload
changes still requires explicit user confirmation.

### Show policy

```text
args: list-policy
```

### Generate default cluster-wide read-only RBAC YAML

```text
args: readonly-rbac
```

Default objects:

- namespace: `gal-safe`
- ServiceAccount: `gal-safe-reader`
- ClusterRole: `gal-safe-reader-readonly`
- ClusterRoleBinding: `gal-safe-reader-readonly`

To apply it after user confirmation, existing generated objects are backed up
first if they already exist:

```text
args: readonly-rbac --apply
```

### Add writable namespace RBAC

Always use the script; never hand-write this YAML for a user request.

```text
args: namespace-write-rbac AAA
```

If `AAA` is protected, the script rejects it. If allowed, it prints a
namespace-scoped `Role` and `RoleBinding` for the existing `gal-safe-reader`
ServiceAccount.

To apply after showing the summary and getting explicit user confirmation, the
existing Role and RoleBinding are backed up first if present:

```text
args: namespace-write-rbac AAA --apply
```

### Generate restricted kubeconfig

```text
args: gen-kubeconfig
```

Creates a ServiceAccount token, reads the cluster server/CA from the current
context, builds a restricted kubeconfig, and writes it to
`~/.safe-mount-dir/gal-k8s-safe/kubeconfig` with mode 0600. The token is never
printed. Options:

- `--service-account` (default `gal-safe-reader`)
- `--service-account-namespace` (default `gal-safe`)
- `--duration` (default `72h`; accepts any Go duration string such as `24h`, `72h`, `168h` (7d), `720h` (30d). Longer = less secure. The token expires after this duration; re-run `gen-kubeconfig` to renew.)
- `--out` (default `~/.safe-mount-dir/gal-k8s-safe/kubeconfig`; refuses paths under `~/.gal`)
- `--dry-run` prints the kubeconfig with the token redacted and writes nothing

> **kubectl version note.** On kubectl >= 1.24 the token is short-lived and
> honors `--duration` (via `kubectl create token`). On older clients (< 1.24)
> the command automatically falls back to the ServiceAccount's long-lived token
> secret; `--duration` cannot be enforced and the token stays valid until the
> ServiceAccount or secret is deleted. The script prints a note when this
> happens. Prefer upgrading kubectl to >= 1.24 for short-lived tokens.

Preview without writing:

```text
args: gen-kubeconfig --dry-run
```

The script refuses to proceed if the cluster has no `certificate-authority-data`
and is not `insecure-skip-tls-verify`; in that case ask the admin for the
correct CA handling instead of copying the admin kubeconfig.

### Renew token in existing kubeconfig

```text
args: renew-token
```

Renews the SA token in an existing restricted kubeconfig. Reads the existing
file to preserve server/CA/context, requests a new token, and rewrites the file
in place with mode 0600. On kubectl >= 1.24 the old token is immediately
invalidated; on older clients the same version fallback as `gen-kubeconfig`
applies (long-lived secret token, `--duration` not enforced). Options:

- `--service-account` (default `gal-safe-reader`)
- `--service-account-namespace` (default `gal-safe`)
- `--duration` (default `72h`; same range as `gen-kubeconfig`)
- `--out` (default `~/.safe-mount-dir/gal-k8s-safe/kubeconfig`; must match the
  path used by `gen-kubeconfig`)
- `--dry-run` prints the new kubeconfig with the token redacted and writes
  nothing

Preview before renewing:

```text
args: renew-token --dry-run
```

### Back up one object

```text
args: backup AAA deployment my-api
```

This writes one YAML backup and prunes backups older than 15 days.

### Guarded apply

Use for safe namespace-scoped manifest changes. It rejects protected namespaces
and manifests containing blocked kinds such as CRDs, Secrets, RBAC, ServiceAccount,
Namespace, Node, storage, and admission webhook resources.

Dry run:

```text
args: guarded-apply AAA /path/to/manifest.yaml --dry-run
```

Apply. The script derives each object from the manifest, then backs up every existing target object before the write:

```text
args: guarded-apply AAA /path/to/manifest.yaml
```

Missing target objects are reported as `Backup skipped (not found)` because there is no previous state to save.

For stdin, set the tool `input` to the manifest and use:

```text
args: guarded-apply AAA -
```

### Rollout restart

This backs up the target object before restarting it:

```text
args: restart AAA deployment my-api
```

Use `--dry-run` to verify policy and create the backup without restarting.

## Generate a restricted kubeconfig

Run these steps only from a trusted admin session that already has permission to
create Kubernetes RBAC objects and service-account tokens. Never mount or copy a
personal/admin kubeconfig into GAL safe mode.

Defaults used by the script: ServiceAccount `gal-safe-reader` in namespace
`gal-safe`, token duration `72h`, output `~/.safe-mount-dir/gal-k8s-safe/kubeconfig`,
and the cluster from `kubectl config current-context`. Override any of these with
the `gen-kubeconfig` flags in step 3.

### 1. Create default read-only RBAC

Prefer using the script:

```text
args: readonly-rbac
```

Review the YAML, then apply after confirmation:

```text
args: readonly-rbac --apply
```

Equivalent YAML shape:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: gal-safe
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: gal-safe-reader
  namespace: gal-safe
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: gal-safe-reader-readonly
rules:
- apiGroups: ["*"]
  resources: ["*"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: gal-safe-reader-readonly
subjects:
- kind: ServiceAccount
  name: gal-safe-reader
  namespace: gal-safe
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: gal-safe-reader-readonly
```

### 2. Optionally grant write access to one namespace

For a user request such as "add AAA namespace write access", call:

```text
args: namespace-write-rbac AAA
```

If the script allows it, summarize:

- namespace: `AAA`
- verbs: `create`, `update`, `patch` plus read verbs
- deletes: not allowed
- low-level/platform resources: not writable
- backups: required before write operations

Then ask for confirmation before applying:

```text
args: namespace-write-rbac AAA --apply
```

### 3. Write the restricted kubeconfig to the safe source path

Use the script command — it requests the SA token, builds the kubeconfig, and
writes it to the safe mount path with mode 0600 without ever printing the token:

```text
args: gen-kubeconfig
```

Preview first if you want to review the structure (token redacted):

```text
args: gen-kubeconfig --dry-run
```

Override defaults as needed, for example a custom namespace or duration:

```text
args: gen-kubeconfig --service-account-namespace gal-safe --service-account gal-safe-reader --duration 168h
```

The script refuses to write under `~/.gal`, and refuses to proceed when the
cluster has no `certificate-authority-data` and is not
`insecure-skip-tls-verify`; in that case ask the admin for the correct CA
handling instead of copying the admin kubeconfig.


### 4. Configure the target GAL agent mount

In `/admin`, edit the target agent config:

```yaml
safe_mode:
  enabled: true
  mounts:
    - source: ~/.safe-mount-dir/gal-k8s-safe/kubeconfig
      target: ~/.kube/config
      mode: ro
```

### 5. Verify inside GAL safe mode

From the target agent:

1. Check `_status` shows Kubernetes/cloud credential dirs/env vars are hidden.
2. Check `_status` lists `~/.kube/config: read-only (safe mount from ...)`.
3. Run non-secret checks, for example:

```sh
kubectl config current-context
kubectl auth can-i --list
kubectl get pods -A
```

If access is too broad, tighten the ClusterRole. If access is denied, adjust the
RBAC or TokenRequest duration. Do not bypass safe mode by mounting the user's
normal `~/.kube/config`.
